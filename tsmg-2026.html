Depth-Guided Precision Fertilization

Broadcast fertilizer application treats a field as uniform, delivering the same rate to bare soil that it delivers to dense canopy. The waste is both economic and environmental. Fixing it means applying only where plant material actually is — which requires a perception system that runs in real time on a moving implement, outdoors, without a network connection or a depth-sensor budget.

The constraint that shapes everything here is cost. Depth sensing is the natural way to separate canopy from background, and LiDAR is the natural way to get depth — but LiDAR units run $5,000 to $15,000, which is not a number that survives contact with a working farm. So the system infers depth from a single RGB camera instead, using monocular depth estimation, and eliminates the hardware entirely.

Pipeline

The zone abstraction is the central design choice, and it is a deliberate refusal to be clever. Targeting individual plants would demand actuation precision the hardware does not have. Instead detections collapse into a union mask that gets integrated over three horizontal bands matched to the nozzle bar. It degrades gracefully under partial or noisy detection, and it maps onto a handful of GPIO lines rather than a servo-aimed boom.

That is perception engineered down to what the actuator can actually do — a detector that misses half a canopy still activates the right zone, because the zone only needs 25% coverage to fire.

Making relative depth metric

MiDaS has a property that makes it awkward for this job: it returns affine-invariant relative inverse depth, not metres. It tells you what is nearer and what is further, on an arbitrary scale that shifts between frames. Deciding whether canopy is within spraying range needs real distance.

The fix is a single reference measurement. With one reading taken at a known two-foot standoff, the scale can be anchored:

metric  = SCENE_1_SHIFT × dmax           # first-order linear
D_ref   = 2.0 × (dmax_scene_1 / dmax)^s  # power-law refinement, s = 3.2

A purely linear model fits badly, because inverse depth and physical distance are related non-linearly — roughly D = 1/(ad + b). So the estimate is refined with a power law anchored at the same reference point. The exponent controls how sharply estimated distance falls off, and was chosen to maximize resolution at close range, where canopy proximity actually matters and where a spraying decision is actually made.

One calibration measurement replaces a depth sensor. That is the whole trick, and it is what makes the cost argument work.

Running it fast enough

Two neural networks per frame on a Jetson Nano started at 2 FPS, which is not real time on a moving implement. Getting to 15 FPS came from choosing a smaller depth backbone and then removing overhead everywhere it hid:

Custom metric-distance algorithms made the smaller 100–150MB MiDaS models viable, which is what unlocked the speedup.

On top of the model swap: FP16 inference, channels_last memory format, Conv+BN folding via YOLO's fuse(), cudnn.benchmark, and inference wrapped in no_grad(). Throughput is tracked with an exponential moving average so a single slow frame doesn't read as a regression.

The detector itself was trained across 10+ YOLO model variants on a 1,000+ image dataset on Google Cloud GPUs, tuned by confusion-matrix and precision–recall analysis for a 30% mAP improvement. The research log below covers that work as it happened.

Bringing up the hardware

The GPIO work was staged so that each step isolated exactly one unknown — a habit that pays for itself the first time something doesn't work and you know precisely which layer to blame.

  • Stage 1Single toggle via gpiod v2 — electrical continuity only
  • Stage 2Sustained 1s toggle loop via gpiod legacy — does it hold up over time
  • Stage 3Same loop through Jetson.GPIO on BOARD pin 7 — library and pin convention
  • Stage 4Keyboard-driven two-channel control on pins 7 and 33 — independent channels

The first working design then had to be thrown away. With only two pins available for three zones, v1 used a combinatorial encoding — pin1 = top OR middle, pin2 = top OR bottom. It worked until two zones needed to be active at once, at which point the encoding could not represent the state without transient conflicts: brief moments where a nozzle fired that shouldn't have. v2 uses three pins, one per zone, on BOARD 7 / 33 / 35. Less elegant, and correct.

The pipeline also degrades rather than dying when the hardware isn't there — Jetson.GPIO is imported inside a try/except, and its absence disables GPIO output so the vision stack still runs on a laptop for development.

  • ActuationJetson.GPIO, 3 lines on BOARD pins 7 / 33 / 35, one per nozzle zone

Limitations

  • Depth is affine-invariant and calibrated from a single reference point, with a hand-fitted exponent. Calibration error across a full distance sweep is still being measured.
  • dmax is sensitive to a single outlier pixel, and there is no temporal filtering on the depth signal.
  • The 25% coverage threshold is hard, with no hysteresis — a zone hovering near the boundary will chatter.
  • Axis-aligned bounding boxes inflate measured coverage relative to actual canopy area.
  • Zones are equal image thirds rather than being calibrated to real spray geometry.
  • Formal per-zone activation accuracy and on-hardware throughput evaluation are still being collected; the public project page deliberately publishes no results until they are.
